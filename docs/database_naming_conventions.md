# Database Naming conventions

## Identifiers (tables, columns, etc)

- Use snake_case and lowercase (avoids mandatory quoting).
- Tables in plural (users, sales_orders); columns in singular.
- Avoid cryptic abbreviations; prioritize clarity.

## Common columns

- Primary key: `id` (use `GENERATED BY DEFAULT AS IDENTITY`).
- Foreign key: `\<entity\>_id` (e.g., `user_id`, `order_id`).
  - Notice that `<entity>` is on singular form.
- Dates/times: *_at (timestamp), *_date (date), *_on (business date).
- Booleans: `is_*`, `has_*`, `can_*` (e.g., `is_active`, `has_discount`).

## Special tables

- Join tables for N:N: `<table_a>_<table_b>` (alphabetical order), e.g., `roles_users`.
- Lookup tables: plural and descriptive, e.g., `countries`, `currencies`.

## Schemas

- Use schemas for functional domains: `auth`, `sales`, `inventory`…
- Schema names in snake_case (e.g., `domain_billing`).

## Constraint/index names (pattern)

- PK: `pk_<table>`
- FK: `fk_<table>__<column>`
- Unique: `uk_<table>__<column[_column2]>`
- Check: `ck_<table>__<column[_condition]>`
- Index (non-unique): `idx_<table>__<column[_column2]>`
  - For search improvement: `idx_sh_<table>__<column[_column2]>`
  - For Uniqueness: `idx_uk_<table>__<column[_column2]>`
  - For FK: `idx_fk_<table>__<column[_column2]>`
- Exclusion: `xk_<table>__<description>`
- Sequence (if needed): `<table>_<column>_seq`
- View/materialized view: `v_<subject>` / `mv_<subject>`
- Function: `fn_<subject>[_<variant>]`
- Trigger: `trg_<table>__<event>__<purpose>`

## Reserved words and collisions

- Avoid reserved words (e.g., `user`, `order`, `table`, `select`).
- If unavoidable, qualify them: `app_user`, `sales_order`.

## Types and enums

- Domains: `dm_<subject>` (e.g., `dm_email`).
- Enums: `enum_<subject>` with values in snake_case.

## Documentation

- Use `COMMENT ON` always that is possible.
  - Describe the domain and semantical content;
- Keep this checklist in the repo and enforce it in migrations/PRs
